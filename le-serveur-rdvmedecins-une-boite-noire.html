    8. Le serveur RdvMedecins, une boîte noire

    Les exemples 22 à 25, puis l'étude de cas, dialoguent avec un serveur : le serveur JSON de l'application [RdvMedecins]. C'est le serveur [NestJS] des cours [React], [Vue.js], [Angular] et [Flutter] : celui du cours [NestJS], dont les contrôleurs ne fabriquent plus des pages HTML mais des réponses JSON. Le lecteur de ces cours connaît déjà ce chapitre, repris ici presque sans changement ; il peut se contenter de la section sur l'authentification, qui explique ce qui change pour une application mobile.

    Dans ce cours, ce serveur est une boîte noire : on n'a pas besoin de savoir comment il est écrit. Seule compte son API, c'est-à-dire la liste des requêtes HTTP qu'il accepte et des réponses qu'il renvoie. C'est la situation ordinaire d'un développeur de client : l'API est un contrat, et l'équipe du serveur peut changer tout ce qu'elle veut derrière ce contrat. Son code source est fourni (dossier [rdvmedecins-nestjs-json]) et abondamment commenté, pour le lecteur curieux.

    Ce chapitre explique comment installer le serveur, décrit son API, et l'interroge avec [curl].

    8.1. L'application RdvMedecins

    L'application gère les rendez-vous d'un cabinet médical. Elle a trois rôles :

    Rôle
    Qui
    Ce qu'il peut faire
    [ADMIN]
    l'administrateur ([admin])
    prendre et annuler les rendez-vous de tous les patients ; gérer les médecins et les clients
    [DOCTOR]
    les médecins ([pelissier], [tatou], [dupont])
    prendre et annuler les rendez-vous de tous les patients ; voir tous les noms dans les agendas
    [USER]
    les patients ([martin], [durand], [bistrou], [german])
    réserver pour eux-mêmes ; annuler leur rendez-vous ; gérer leur compte. Dans un agenda, ils ne voient pas le nom des autres patients

    Les comptes de démonstration ont pour mot de passe leur login. Les règles de gestion sont vérifiées par le serveur, quel que soit le client :

    • pas de rendez-vous dans le passé ;
    • un seul rendez-vous à venir par patient ;
    • un créneau n'est réservé qu'une fois par jour ;
    • deux médecins (ou deux clients) ne portent pas les mêmes prénom et nom ; un login n'appartient qu'à un compte ;
    • un médecin qui a des rendez-vous ne peut pas être supprimé ;
    • une fiche modifiée entre-temps par quelqu'un d'autre ne peut pas être écrasée (verrou optimiste) ;
    • un patient ne reçoit jamais le nom d'un autre patient.

    8.3. Le format des réponses

    Toutes les routes commencent par [/api]. Une requête réussie reçoit un code 2xx et, dans son corps, les données demandées, en JSON. Une requête refusée reçoit un code 4xx ou 5xx et, TOUJOURS, un corps de la même forme :

    1
2
3
4
5
6
    {
  "statusCode": 400,
  "cle": "ERRORS.INVALID_FORM",
  "params": { "min": "6" },
  "champs": { "nom": "ERRORS.LASTNAME_REQUIRED", "password": "ERRORS.PASSWORD_TOO_SHORT" }
}
    • [statusCode] : le code HTTP, répété dans le corps ;
    • [cle] : la clé de traduction du message. Le serveur ne renvoie jamais de texte à afficher : il ne connaît plus la langue de l'utilisateur. C'est le client qui traduit la clé avec ses dictionnaires (cf. exemple 21) ;
    • [params] (facultatif) : les paramètres des messages ([Au moins {min} caractères], [Réessayez dans {minutes} minute(s)]) ;
    • [champs] (facultatif) : pour un formulaire refusé, l'erreur de chaque champ.

    401
    pas authentifié

    8.4. L'authentification

    Le client s'authentifie par [POST /api/auth/login], avec login, mot de passe et réponse au captcha. En retour, le serveur envoie, dans l'entête [Set-Cookie] de sa réponse, un cookie qui contient un jeton JWT signé :

    1
    Set-Cookie: rdvmedecins_jwt=eyJhbGciOiJIUzI1NiIs...; Max-Age=7200; Path=/api; HttpOnly; SameSite=Strict

    Le client doit ensuite présenter ce cookie, dans l'entête [Cookie], à chaque requête vers [/api] : c'est ainsi que le serveur sait qui l'interroge.

    Ce serveur a été écrit pour des clients web, et ses choix s'expliquent par les dangers propres aux navigateurs :

    • [HttpOnly] : le code [JavaScript] de la page ne peut PAS lire ce cookie. Un script malveillant qui aurait été injecté dans la page ne pourrait donc pas voler le jeton. Conséquence pour le client : il ne sait pas, par lui-même, s'il est connecté. Il le demande au serveur ([GET /api/auth/moi]) ;
    • [Path=/api] : le cookie n'est joint qu'aux requêtes vers l'API ;
    • [SameSite=Strict] : le navigateur ne joint le cookie qu'aux requêtes émises DEPUIS une page de ce site. Une page piégée sur un autre site ne peut pas faire agir le navigateur au nom de l'utilisateur (attaque dite CSRF) ;
    • [Max-Age=7200] : il disparaît au bout de deux heures, en même temps que le jeton expire.

    Une seconde protection contre les attaques CSRF : le serveur refuse (415) toute requête POST dont le corps n'est pas en JSON. Un formulaire HTML piégé, sur un autre site, ne sait pas envoyer de JSON.

    Et pour une application mobile ? Il n'y a pas de navigateur : personne ne range le cookie ni ne le renvoie tout seul. C'est l'application qui jouera ce rôle : la bibliothèque [OkHttp], à qui l'on confie un « bocal à cookies » (un [CookieJar]), lit l'entête [Set-Cookie] des réponses et écrit l'entête [Cookie] des requêtes (exemple 23). Les attributs [HttpOnly] et [SameSite] ne concernent que les navigateurs : ils sont sans effet sur elle, comme sur [curl].

    8.6. Interroger l'API avec curl

    Le dossier [curl] du serveur contient les corps JSON des requêtes de ce chapitre, un fichier par requête. Par exemple, [curl/login-admin.json] :

    1
    { "login": "admin", "password": "admin", "captchaId": "-", "captcha": "test" }

    Les commandes se tapent dans une console ouverte sur le dossier [rdvmedecins-nestjs-json]. Quelques options de [curl] :

    • [-i] : afficher aussi les entêtes de la réponse ; [-s] : sans barre de progression ;
    • [--json @fichier] : envoyer le contenu du fichier en POST, avec l'entête [Content-Type: application/json] (curl 7.82 et plus ; avec une version plus ancienne, on écrit [-H "Content-Type: application/json" -d @fichier]) ;
    • [-X PUT], [-X DELETE] : la méthode HTTP ;
    • [-c cookies.txt] : enregistrer les cookies reçus dans ce fichier ; [-b cookies.txt] : les renvoyer. C'est ainsi que [curl] « reste connecté » d'une commande à l'autre, comme le ferait un navigateur.

    Sous [PowerShell], il faut taper [curl.exe] et non [curl] (qui y désigne une autre commande). Les réponses JSON un peu longues ont été mises en forme pour ce document, et les entêtes [Date], [ETag], [Connection] et [Keep-Alive] retirés.
